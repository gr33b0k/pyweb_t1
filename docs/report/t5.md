# T5. Публикуемость и цитируемость результата

## Цель работы

Цель задания — определить, какие возможности предоставляют генераторы статических сайтов для публикации результатов исследования и какие дополнительные средства необходимы для того, чтобы такой сайт можно было рассматривать как полноценный научный результат.

В работе рассматриваются четыре генератора, использовавшиеся при выполнении предыдущих заданий:

- **MkDocs + Material**;
- **Sphinx + MyST-Parser**;
- **Pelican**;
- **Quarto**.

Для каждого механизма используется следующая классификация:

| Обозначение       | Значение                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------- |
| Из коробки        | возможность предоставляется самим генератором или основной рассматриваемой темой и не требует стороннего расширения |
| Плагин/расширение | требуется установка дополнительного пакета или расширения                                                           |
| Вручную           | механизм реализуется собственным шаблоном, статическим файлом, скриптом или внешней системой                        |

Под «публикацией» в данной работе понимается не просто размещение HTML-файлов в интернете, а результат, который можно однозначно идентифицировать, процитировать, найти и связать с конкретной версией исходного кода и данных.

## 1. Постоянные ссылки и стабильность URL

Для цитирования необходимо, чтобы ссылка на опубликованный материал сохранялась после повторной сборки сайта. Обычная пересборка не должна изменять URL, если не меняется структура исходных документов или настройки генерации адресов.

Все четыре генератора позволяют управлять URL на уровне структуры сайта. При этом важно различать **стабильность при пересборке** и **сохранение URL после переименования страницы**. Во втором случае требуется дополнительная политика редиректов или сохранение старой страницы.

MkDocs по умолчанию формирует страницы из Markdown-файлов, а итоговая структура зависит в том числе от `use_directory_urls`. Сам MkDocs также генерирует `sitemap.xml`.

Sphinx формирует адреса из имен документов и поддерживает постоянные якоря и различные HTML-билдеры. Для канонического адреса сайта предусмотрен параметр `html_baseurl`.

Pelican предоставляет отдельные настройки `*_URL` и `*_SAVE_AS`, позволяющие независимо задавать публичный URL и путь сохранения файла. URL может строиться, например, из `slug`.

Quarto использует структуру проекта и настройки сайта для формирования адресов. Для сайтов также существует `site-url`, который используется при формировании абсолютных адресов и связанных с ними метаданных.

| Возможность                                 |        MkDocs + Material |        Sphinx + MyST |              Pelican |         Quarto |
| ------------------------------------------- | -----------------------: | -------------------: | -------------------: | -------------: |
| Стабильный URL при обычной пересборке       |           **Из коробки** |       **Из коробки** |       **Из коробки** | **Из коробки** |
| Настройка структуры URL                     |           **Из коробки** |       **Из коробки** |       **Из коробки** | **Из коробки** |
| Явное задание URL страницы                  | **Из коробки / Вручную** |       **Из коробки** |       **Из коробки** | **Из коробки** |
| Сохранение старого URL после переименования |     **Плагин / Вручную** | **Плагин / Вручную** |          **Вручную** |    **Вручную** |
| Проверка внутренних ссылок                  |           **Из коробки** |       **Из коробки** | **Плагин / Вручную** | **Из коробки** |

Таким образом, генератор способен обеспечить технически стабильные адреса, но **сам по себе URL не становится постоянным идентификатором публикации**. Для научного цитирования желательно не переименовывать уже опубликованные страницы, а при необходимости изменения адреса использовать редирект со старого URL на новый.

## 2. Версионирование сайта, кода и данных

Одной ссылки на текущую версию сайта недостаточно для воспроизводимого исследования. Если опубликованный результат изменился, необходимо иметь возможность определить, какая именно версия кода и данных использовалась для получения результата.

Для этого можно использовать два связанных уровня:

1. **версионирование исходного проекта** с помощью Git;
2. **публикацию нескольких версий самого сайта**

Git не является частью генераторов статических сайтов, поэтому хранение истории коммитов относится к внешней инфраструктуре.

Для MkDocs существует `mike`, который интегрируется с Material и позволяет публиковать несколько версий документации в отдельных каталогах. Material предоставляет для этого встроенный селектор версий.

Для Sphinx существует расширение `sphinx-multiversion`, которое позволяет собирать документацию различных веток и тегов в одном опубликованном наборе документации.

Pelican и Quarto не требуют использовать определенную систему версионирования исходников: Git, теги и отдельные каталоги можно организовать независимо от генератора.

| Механизм                        |        MkDocs + Material |                    Sphinx + MyST |     Pelican |                   Quarto |
| ------------------------------- | -----------------------: | -------------------------------: | ----------: | -----------------------: |
| Работа с Git                    |              **Вручную** |                      **Вручную** | **Вручную** |              **Вручную** |
| Вывод номера версии             | **Из коробки / Вручную** |                   **Из коробки** | **Вручную** | **Из коробки / Вручную** |
| Несколько опубликованных версий |        **Плагин — mike** | **Плагин — sphinx-multiversion** | **Вручную** |              **Вручную** |
| Переключатель версий            |  **Из коробки + Плагин** |             **Плагин + Вручную** | **Вручную** |              **Вручную** |
| Связь с Git tag/release         |              **Вручную** |             **Плагин / Вручную** | **Вручную** |              **Вручную** |
| Вывод версии данных             |              **Вручную** |                      **Вручную** | **Вручную** |              **Вручную** |

Отдельно необходимо хранить версию или хеш набора данных. Генератор статического сайта не может автоматически определить научную связь между конкретным графиком и набором данных, поэтому такую информацию следует добавлять в метаданные или формировать скриптом сборки.

Например, для опубликованного результата можно указывать:

```text
Версия публикации: 1.2.0
Коммит: 8f31c2a
Набор данных: dataset-v2
Дата сборки: 2026-10-01
```

Такой подход позволяет связать страницу сайта с конкретным состоянием репозитория.

## 3. DOI и ORCID

### 3.1. DOI

DOI является постоянным идентификатором цифрового объекта, а не обычным URL страницы. Поэтому генератор статических сайтов не должен рассматриваться как система присвоения DOI.

Типовая схема публикации результата выглядит следующим образом:

```text
GitHub repository
       ↓
Git tag
       ↓
GitHub Release
       ↓
Zenodo
       ↓
DOI
       ↓
страница публикации / метаданные
```

В этом процессе генератор отвечает только за формирование сайта. Архивирование версии и присвоение постоянного идентификатора выполняются внешней системой.

Таким образом:

| Возможность                        |                   MkDocs |                   Sphinx |                  Pelican |                   Quarto |
| ---------------------------------- | -----------------------: | -----------------------: | -----------------------: | -----------------------: |
| Автоматическое присвоение DOI      |              **Вручную** |              **Вручную** |              **Вручную** |              **Вручную** |
| Указание уже полученного DOI       | **Вручную / Из коробки** | **Вручную / Из коробки** | **Вручную / Из коробки** |           **Из коробки** |
| Создание страницы «Как цитировать» |              **Вручную** |              **Вручную** |              **Вручную** | **Из коробки / Вручную** |

Quarto имеет наиболее развитую встроенную модель библиографических метаданных: в YAML можно указать DOI, авторов, тип публикации и другие поля CSL, а для веб-статей можно автоматически сформировать представление цитирования.

При этом даже Quarto **не присваивает DOI самостоятельно**: наличие поля `doi` означает указание уже существующего идентификатора.

### 3.2. ORCID

ORCID предназначен для однозначной идентификации автора. Это постоянный идентификатор человека, в отличие от DOI, который используется для идентификации исследовательского объекта.

| Генератор         |          ORCID |
| ----------------- | -------------: |
| MkDocs + Material |    **Вручную** |
| Sphinx + MyST     |    **Вручную** |
| Pelican           |    **Вручную** |
| Quarto            | **Из коробки** |

Quarto поддерживает `orcid` непосредственно в структуре `author`, после чего идентификатор может быть использован в сгенерированных форматах публикации.

В остальных генераторах ORCID можно добавить через собственные шаблоны и HTML-метаданные.

## 4. Метаданные для индексации

Для научной публикации недостаточно только HTML-текста. Важную роль играют машиночитаемые метаданные.

В работе рассматриваются:

- **Highwire Press / Google Scholar metadata**;
- **Dublin Core**;
- **Open Graph**;
- **`sitemap.xml`**;
- **`robots.txt`**;
- канонический URL.

### Highwire Press

Мета-теги вида:

```html
<meta name="citation_title" content="..." />
<meta name="citation_author" content="..." />
<meta name="citation_publication_date" content="..." />
```

позволяют поисковым системам извлекать библиографические сведения о документе.

Quarto имеет специальный режим `google-scholar: true`, который генерирует соответствующие научные метаданные на основе полей цитирования. Документация Quarto показывает генерацию `citation_title`, `citation_author`, `citation_publication_date`, `citation_doi` и других тегов.

Для MkDocs, Sphinx и Pelican такие специализированные научные метаданные обычно требуют шаблона или расширения.

### Dublin Core

Dublin Core не является обязательной функцией какого-либо из рассматриваемых генераторов. Универсальный вариант — добавить соответствующие `<meta>`-элементы через шаблон.

### Open Graph

Open Graph используется преимущественно для формирования корректного представления ссылки при публикации в социальных сетях и мессенджерах.

Material for MkDocs содержит встроенный плагин social, который создает social cards и соответствующие метаданные. Дополнительный пакет самого плагина устанавливать не требуется, хотя для генерации изображений необходимы зависимости обработки изображений.

В Sphinx для этого можно использовать `sphinxext-opengraph`, который устанавливается отдельно.

Quarto поддерживает `open-graph` непосредственно в настройках сайта.

### Sitemap

` sitemap.xml` помогает поисковым системам обнаруживать опубликованные страницы.

MkDocs генерирует `sitemap.xml` непосредственно при сборке сайта.

Для Sphinx существует отдельное расширение `sphinx-sitemap`.

Для Pelican sitemap реализуется через plugin ecosystem.

В Quarto `site-url` используется в том числе для механизмов, связанных с sitemap и абсолютными адресами сайта.

### Сводная таблица метаданных

| Механизм                  | MkDocs + Material |            Sphinx + MyST |                  Pelican |         Quarto |
| ------------------------- | ----------------: | -----------------------: | -----------------------: | -------------: |
| Highwire / Google Scholar |       **Вручную** |     **Вручную / Плагин** |              **Вручную** | **Из коробки** |
| Dublin Core               |       **Вручную** |              **Вручную** |              **Вручную** |    **Вручную** |
| Open Graph                |    **Из коробки** |               **Плагин** |     **Плагин / Вручную** | **Из коробки** |
| `sitemap.xml`             |    **Из коробки** |               **Плагин** |               **Плагин** | **Из коробки** |
| `robots.txt`              |       **Вручную** |              **Вручную** |              **Вручную** |    **Вручную** |
| Canonical URL             |    **Из коробки** |           **Из коробки** | **Вручную / Из коробки** | **Из коробки** |
| Meta description          |    **Из коробки** | **Из коробки / Вручную** |           **Из коробки** | **Из коробки** |

Таким образом, наличие `sitemap.xml` и Open Graph нельзя напрямую считать доказательством научной индексации. Эти механизмы улучшают обнаружение и представление сайта, но для Google Scholar важны прежде всего корректные библиографические метаданные и содержание, соответствующее требованиям поисковой системы.

## 5. Лицензирование

Полноценная публикация должна явно определять условия использования разных составляющих результата.

На практике целесообразно разделять как минимум:

1. текст и изображения;
2. программный код;
3. исходные данные.

Например:

| Объект               | Возможный вариант                 |
| -------------------- | --------------------------------- |
| Текст и изображения  | CC BY 4.0                         |
| Исходный код         | MIT                               |
| Открытые данные      | CC BY 4.0 / CC0 1.0               |
| Сторонние компоненты | лицензия соответствующего проекта |

Выбор конкретной лицензии зависит от происхождения материала и условий распространения. Сам генератор сайта не определяет лицензионные права автора.

| Генератор |        Лицензия контента | Лицензия кода | Лицензия данных |
| --------- | -----------------------: | ------------: | --------------: |
| MkDocs    |              **Вручную** |   **Вручную** |     **Вручную** |
| Sphinx    |              **Вручную** |   **Вручную** |     **Вручную** |
| Pelican   |              **Вручную** |   **Вручную** |     **Вручную** |
| Quarto    | **Из коробки / Вручную** |   **Вручную** |     **Вручную** |

Quarto позволяет указывать лицензионные и библиографические сведения в метаданных документа, однако это не заменяет выбор и хранение соответствующей лицензии для исходного кода и данных.

Следовательно, лицензирование следует рассматривать как **свойство всего исследовательского результата**, а не как преимущество конкретного генератора.

## 6. Соответствие принципам FAIR

FAIR — это набор принципов, направленных на повышение обнаруживаемости, доступности, совместимости и повторного использования исследовательских результатов.

Для рассматриваемой публикации их можно интерпретировать следующим образом:

| Принцип           | Требование                                                    | Средства реализации                                         |
| ----------------- | ------------------------------------------------------------- | ----------------------------------------------------------- |
| **Findable**      | результат можно найти и однозначно идентифицировать           | DOI, ORCID, sitemap, метаданные, стабильные URL             |
| **Accessible**    | результат и его метаданные доступны по стандартным протоколам | HTTPS, статический сайт, архив публикации                   |
| **Interoperable** | используются стандартные форматы                              | HTML, Markdown, JSON, CSV, BibTeX, Dublin Core, CSL         |
| **Reusable**      | результат можно использовать повторно                         | лицензия, версия, описание данных, документация, provenance |

Ни один из генераторов не обеспечивает выполнение FAIR целиком.

Например, наличие `sitemap.xml` помогает с **Findable**, но не обеспечивает идентификацию версии. DOI повышает обнаруживаемость и идентифицируемость, но не гарантирует наличие лицензии или открытых данных.

Поэтому FAIR относится не к отдельному генератору, а к совокупности:

```text
исходный код
      +
данные
      +
генератор
      +
хостинг
      +
архив
      +
метаданные
      +
лицензия
      +
идентификаторы
```

| Генератор         | FAIR без дополнительной настройки |
| ----------------- | --------------------------------: |
| MkDocs + Material |                          Частично |
| Sphinx + MyST     |                          Частично |
| Pelican           |                          Частично |
| Quarto            |                          Частично |

## 7. Что можно реализовать на Helios

Статический генератор создает набор файлов HTML, CSS, JavaScript, изображений и XML/текстовых ресурсов. Поэтому большая часть механизмов, относящихся непосредственно к содержимому сайта, не требует специальной серверной поддержки.

На Helios могут быть размещены:

- HTML-страницы;
- CSS и JavaScript;
- изображения и другие статические ресурсы;
- `sitemap.xml`;
- `robots.txt` как файл сайта;
- Open Graph и другие HTML-метаданные;
- страницы с указанием ORCID;
- файлы лицензий;
- различные версии сайта в отдельных каталогах.

При этом необходимо разделять **возможность разместить файл** и **возможность управлять HTTP-сервером**.

Например, собственный статический `404.html` или HTML-редирект можно подготовить средствами генератора, но серверный HTTP-редирект `301` требует соответствующей настройки веб-сервера.

| Механизм                       | Helios                              |
| ------------------------------ | ----------------------------------- |
| Статический HTML               | **Да**                              |
| CSS / JavaScript / изображения | **Да**                              |
| Open Graph                     | **Да**                              |
| Highwire metadata              | **Да**                              |
| Dublin Core                    | **Да**                              |
| `sitemap.xml`                  | **Да**                              |
| ORCID в HTML                   | **Да**                              |
| Лицензии                       | **Да**                              |
| Несколько версий в каталогах   | **Да**                              |
| DOI                            | **Да, через внешний сервис**        |
| GitHub Release                 | **Не зависит от Helios**            |
| `robots.txt`                   | **Ограничено правами пользователя** |

Таким образом, Helios подходит для размещения статической копии публикации, но не заменяет Git-репозиторий и архив научных результатов.

Для долговременной идентификации логичнее разделить функции:

```text
Helios
  ↓
демонстрация опубликованного сайта

GitHub
  ↓
исходный код + история + tags/releases

Zenodo
  ↓
архив версии + DOI

ORCID
  ↓
идентификация автора
```

## 9. Вывод

Проведенное сравнение показывает, что статический сайт сам по себе еще не является полноценной научной публикацией.

Генераторы статических сайтов решают преимущественно задачу **представления результата**: создают HTML, обеспечивают структуру URL, позволяют добавлять метаданные, формируют карту сайта и предоставляют механизмы расширения.

Для полноценной публикации дополнительно необходимы внешние компоненты:

- система контроля версий для исходного кода;
- фиксированные версии результатов;
- архивирование релизов;
- DOI;
- ORCID авторов;
- метаданные научной публикации;
- отдельные лицензии для текста, кода и данных;
- описание происхождения результатов;
- организация данных в пригодных для повторного использования форматах.

Наиболее заметное различие между рассмотренными генераторами заключается не в возможности разместить HTML, а в степени встроенной поддержки **научных метаданных и публикационных сценариев**.

**MkDocs + Material** хорошо подходит для документационного представления результатов и предоставляет развитую систему расширений; в частности, Material имеет встроенные возможности для social metadata, а публикация нескольких версий может выполняться через интеграцию с `mike`.

**Sphinx + MyST** предоставляет развитую систему документации, версий и расширений, однако многие механизмы, связанные непосредственно с публикацией в вебе, подключаются отдельно. Например, для нескольких версий используется `sphinx-multiversion`, а для sitemap — `sphinx-sitemap`.

**Pelican** предоставляет гибкую настройку URL, метаданных и шаблонов, однако значительная часть механизмов поисковой оптимизации и публикационной инфраструктуры реализуется через плагины или собственные шаблоны.

**Quarto** ориентирован не только на документацию, но и на воспроизводимые научные документы. Он предоставляет встроенные средства для библиографических метаданных, ORCID, DOI-полей и генерации Google Scholar metadata.

При этом ни один генератор не заменяет внешнюю инфраструктуру публикации. **DOI, архивирование версии, Git-история и идентификация автора являются отдельными компонентами научного процесса.**

Таким образом, переход от «сайта с результатами» к публикации можно представить следующим образом:

```text
Статический генератор
        ↓
HTML + метаданные + ссылки
        ↓
Хостинг
        ↓
Git + версия исходного кода
        ↓
Release
        ↓
Архивирование
        ↓
DOI + ORCID
        ↓
Цитируемый и воспроизводимый результат
```

Следовательно, выбор генератора определяет удобство формирования и публикации веб-представления результата, но **публикуемость и цитируемость в полном смысле обеспечиваются совокупностью генератора, репозитория, архива, идентификаторов, метаданных, лицензий и хостинга**.
