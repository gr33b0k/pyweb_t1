# P4. Развертывание на Helios с контролем качества доставки

## Цель работы

Цель работы — автоматизировать развертывание статического сайта на сервере Helios ИТМО с использованием SSH и `rsync`, а также обеспечить контроль результата доставки.

В рамках работы необходимо было реализовать:

- автоматическую публикацию сайта на Helios;
- использование отдельного deploy SSH-ключа;
- healthcheck после развертывания;
- публикацию каждой ветки в отдельном preview-каталоге;
- сохранение предыдущей версии сайта;
- возможность возврата к предыдущей версии;
- анализ поведения системы при обрыве развертывания;
- сравнение полученного решения с GitHub Pages.

В качестве статического генератора используется MkDocs.

---

## 1. Используемая инфраструктура

Исходный код сайта хранится в Git-репозитории. Автоматизация развертывания выполняется с помощью GitHub Actions.

После отправки изменений в репозиторий запускается workflow, который собирает сайт и для Helios выполняет последовательность:

```text
Git push
   ↓
GitHub Actions
   ↓
Установка зависимостей
   ↓
Сборка MkDocs
   ↓
Настройка SSH
   ↓
Определение каталога публикации
   ↓
Backup предыдущей версии
   ↓
rsync → Helios
   ↓
Healthcheck
   ↓
Успешное / неуспешное завершение
```

Публичный сайт на Helios размещен по адресу:

<https://se.ifmo.ru/~s508761/mkdocs/ >

---

## 2. Сборка сайта

Перед публикацией выполняется сборка статического сайта командой:

```bash
mkdocs build --strict
```

В результате MkDocs формирует каталог:

```text
site/
```

Именно его содержимое передается на Helios.

Использование параметра `--strict` позволяет завершить сборку с ошибкой при наличии проблем, которые MkDocs обычно может вывести только в виде предупреждений. Благодаря этому некорректно собранный сайт не переходит к этапу публикации.

Зависимости проекта устанавливаются из файла:

```text
requirements.txt
```

В частности, используются MkDocs и тема Material.

---

## 3. Подключение к Helios по SSH

Для автоматического развертывания используется отдельная SSH-пара ключей.

Приватный ключ не хранится в репозитории. Он передается в GitHub Actions через Secret:

```text
PRIVATE_SSH_KEY
```

Также в Secrets хранятся параметры подключения:

| Secret            | Назначение                  |
| ----------------- | --------------------------- |
| `PRIVATE_SSH_KEY` | приватный deploy-ключ       |
| `KNOWN_HOSTS`     | доверенный ключ SSH-сервера |
| `REMOTE_DEST`     | адрес и каталог публикации  |
| `HELIOS_URL`      | публичный URL сайта         |

Во время выполнения workflow ключ записывается в:

```text
~/.ssh/id_ed25519
```

с правами доступа `600`.

Ключ сервера записывается в:

```text
~/.ssh/known_hosts
```

После этого GitHub Actions может выполнять команды на Helios без интерактивного ввода пароля или подтверждения fingerprint.

Такой подход позволяет не хранить учетные данные непосредственно в исходном коде workflow.

---

## 4. Передача файлов через rsync

Для доставки результата сборки используется `rsync` поверх SSH:

```bash
rsync \
  -e "ssh -p 2222" \
  --archive \
  --delete \
  site/ \
  "$REMOTE_PATH"
```

Параметр `--archive` сохраняет структуру передаваемых файлов и основные атрибуты.

Параметр:

```text
--delete
```

удаляет на сервере файлы, которых нет в новой сборке.

Это позволяет поддерживать содержимое каталога публикации в соответствии с текущим состоянием каталога `site/`.

Таким образом, после успешной передачи на Helios находится именно актуальная версия сгенерированного сайта.

## 5. Preview-сборки для отдельных веток

Одним из требований задания является публикация каждой ветки в отдельном подкаталоге.

Для основной ветки `main` используется основной каталог сайта.

Для остальных веток автоматически формируется путь:

```text
preview/<имя-ветки>/
```

При этом символ `/` в названии ветки заменяется на `-`.

Например:

```text
feature/new-page
```

преобразуется в:

```text
feature-new-page
```

и публикуется в:

```text
preview/feature-new-page/
```

В workflow это реализовано следующим образом:

```bash
BRANCH_NAME="${GITHUB_REF_NAME//\//-}"
```

Для основной ветки задаются:

```text
SITE_URL = HELIOS_URL
REMOTE_PATH = REMOTE_DEST
```

Для остальных веток:

```text
SITE_URL = HELIOS_URL/preview/<branch>/
REMOTE_PATH = REMOTE_DEST/preview/<branch>/
```

Перед публикацией preview-каталога на сервере выполняется его создание:

```bash
mkdir -p
```

через SSH.

В результате различные ветки не перезаписывают содержимое друг друга:

```text
mkdocs/
├── index.html
├── ...
└── preview/
    ├── feature-new-page/
    ├── feature-search/
    └── fix-header/
```

Основная ветка при этом остается доступна непосредственно по основному адресу сайта.

## 6. Healthcheck после развертывания

Простой успешный `rsync` еще не означает, что опубликованный сайт действительно работает.

Поэтому после передачи файлов выполняется healthcheck.

Сначала workflow отправляет HTTP-запрос по адресу текущей публикации:

```bash
HTTP_CODE=$(curl \
  -L \
  -s \
  -o response.html \
  -w "%{http_code}" \
  "$SITE_URL")
```

Из ответа сохраняется HTML, а код ответа записывается в переменную `HTTP_CODE`.

Первое условие проверки:

```bash
if [ "$HTTP_CODE" != "200" ]; then
  exit 1
fi
```

Если сервер возвращает код, отличный от `200`, job завершается с ошибкой.

Однако одного HTTP-кода недостаточно. Сервер может вернуть корректный HTML, но содержимое может относиться не к той версии сайта.

Поэтому дополнительно проверяется наличие контрольной строки:

```text
MKDOCS_DEPLOY_TEST_2026
```

Проверка выполняется командой:

```bash
if ! grep -q "MKDOCS_DEPLOY_TEST_2026" response.html; then
  exit 1
fi
```

Таким образом, успешный healthcheck требует выполнения двух условий:

```text
HTTP 200
    +
контрольная строка присутствует
    ↓
Deploy успешно завершен
```

Если хотя бы одно условие не выполнено, GitHub Actions завершает job с ошибкой.

Важно, что healthcheck использует переменную `SITE_URL`. Поэтому при публикации ветки проверяется именно ее preview-адрес, а не основной адрес сайта.

## 7. Резервное копирование предыдущей версии

Перед обновлением основной версии сайта текущий каталог сохраняется в резервную копию.

Используемая схема:

```text
текущая версия
      ↓
<REMOTE_PATH>.backup
      ↓
новая версия
```

Перед копированием старая резервная копия удаляется:

```bash
rm -rf '${REMOTE_PATH}.backup'
```

После этого, если текущий каталог существует, он копируется:

```bash
if [ -d '${REMOTE_PATH}' ]; then
  cp -a '${REMOTE_PATH}' '${REMOTE_PATH}.backup'
fi
```

Таким образом, перед началом нового развертывания на сервере находятся:

```text
REMOTE_PATH
REMOTE_PATH.backup
```

где первый каталог содержит текущую версию, а второй — предыдущую.

Резервное копирование выполняется до `rsync`, поэтому даже при проблеме во время передачи предыдущая версия остается доступной для восстановления.

---

## 8. Откат к предыдущей версии

Если новая версия сайта оказалась некорректной, сохраненную копию можно вернуть.

Например, текущий каталог можно заменить резервной копией:

```bash
rm -rf "$REMOTE_PATH"
mv "${REMOTE_PATH}.backup" "$REMOTE_PATH"
```

После этого сайт снова использует файлы предыдущей версии.

Затем можно повторно выполнить healthcheck:

```bash
curl -L "$HELIOS_URL"
```

и проверить:

- HTTP-код `200`;
- наличие контрольной строки.

Таким образом, откат не требует повторной сборки сайта и позволяет быстро восстановить предыдущий вариант.

В текущей реализации откат выполняется вручную через SSH. Автоматического шага rollback внутри workflow нет.

---

## 9. Поведение при обрыве развертывания

Отдельно необходимо рассмотреть ситуацию, когда соединение с Helios прерывается во время выполнения `rsync`.

Последовательность может выглядеть следующим образом:

```text
Backup
  ↓
Начало rsync
  ↓
Передана часть файлов
  ↓
Обрыв соединения
  ↓
rsync завершается с ошибкой
```

Поскольку `rsync` изменяет целевой каталог непосредственно во время передачи, при обрыве соединения он потенциально может содержать смесь старых и новых файлов.

Однако предыдущая версия была сохранена до начала передачи:

```text
REMOTE_PATH.backup
```

Поэтому поврежденное или неполное состояние можно удалить и восстановить предыдущую версию:

```bash
rm -rf "$REMOTE_PATH"
mv "${REMOTE_PATH}.backup" "$REMOTE_PATH"
```

После восстановления выполняется healthcheck.

Таким образом, обрыв передачи не приводит к потере предыдущей версии сайта.

При этом текущая реализация не выполняет автоматический rollback после обрыва. Workflow фиксирует ошибку доставки, после чего восстановление выполняется вручную.

---

## 10. Почему healthcheck выполняется после rsync

Сам факт успешного выполнения команды:

```bash
rsync ...
```

не гарантирует корректность опубликованного сайта.

Например, сервер может:

- быть недоступен по HTTP;
- возвращать ошибку;
- отдавать страницу с неправильным содержимым;
- содержать неполную версию сайта после проблем с передачей.

Поэтому в pipeline разделены две проверки:

```text
Доставка файлов
      ↓
rsync завершился успешно
      ↓
Проверка опубликованного результата
      ↓
HTTP 200
      ↓
Контрольная строка
```

Это позволяет контролировать не только процесс доставки, но и фактический результат

## 12. Сравнение Helios и GitHub Pages

GitHub Pages в данной работе используется как альтернативный вариант публикации для сравнения с реализованным развертыванием на Helios.

Основные различия:

| Критерий                  | Helios                            | GitHub Pages                                |
| ------------------------- | --------------------------------- | ------------------------------------------- |
| Способ доставки           | SSH + `rsync`                     | инфраструктура GitHub Pages                 |
| Отдельный SSH-ключ        | требуется                         | не требуется                                |
| Доступ к файловой системе | есть через SSH                    | отсутствует                                 |
| Управление каталогами     | пользовательское                  | управляется GitHub                          |
| Низкоуровневая отладка    | SSH, `ls`, `find`, `curl` и т. д. | в основном GitHub Actions и настройки Pages |
| Первоначальная настройка  | сложнее                           | проще                                       |
| Контроль инфраструктуры   | выше                              | ниже                                        |

### Время доставки

При сравнении необходимо учитывать полную продолжительность pipeline, а не только время копирования файлов.

Для Helios в процесс входят:

```text
запуск job
→ установка окружения
→ сборка MkDocs
→ SSH
→ rsync
→ HTTP healthcheck
```

Для GitHub Pages процесс публикации организован инфраструктурой GitHub.

Фактическое время выполнения можно определить по продолжительности соответствующих GitHub Actions jobs:

| Показатель        |  Helios | GitHub Pages |
| ----------------- | ------: | -----------: |
| Сборка            |  `1- с` |       `1- с` |
| Публикация        | `4-5 с` |      `6-8 с` |
| Полное выполнение |  `22 с` |    `22-30 с` |

### Надежность

При использовании Helios результат зависит от нескольких дополнительных компонентов:

- доступности SSH;
- корректности SSH-ключа;
- прав пользователя;
- существования каталогов;
- работы `rsync`;
- доступности веб-сервера.

При этом в реализованной схеме присутствует дополнительная проверка результата через healthcheck и резервная копия предыдущей версии.

GitHub Pages скрывает серверную часть инфраструктуры от пользователя и поэтому требует меньше ручных настроек.

### Удобство отладки

Helios предоставляет непосредственный доступ к серверу.

При возникновении проблемы можно подключиться по SSH и проверить состояние файлов:

```bash
ls -la
```

Можно также проверить содержимое опубликованного сайта:

```bash
find <directory>
```

и HTTP-ответ:

```bash
curl -I <SITE_URL>
```

В GitHub Pages большая часть инфраструктуры скрыта, поэтому диагностика преимущественно выполняется через логи GitHub Actions и настройки Pages.

При этом для стандартной публикации статического сайта такой подход уменьшает количество инфраструктурных компонентов, которыми должен управлять разработчик.

## 13. Результат работы

В результате работы на Helios реализован автоматизированный pipeline публикации статического сайта.

Итоговая схема:

```text
                    Git push
                       │
                       ▼
                GitHub Actions
                       │
                       ▼
              mkdocs build --strict
                       │
                       ▼
                 SSH setup
                       │
              ┌────────┴────────┐
              │                 │
             main            branch
              │                 │
              ▼                 ▼
        основной каталог    preview/<branch>/
              │                 │
              └────────┬────────┘
                       ▼
                     rsync
                       │
                       ▼
                    Helios
                       │
                       ▼
                  Healthcheck
                   /        \
                PASS         FAIL
                 │             │
                 ▼             ▼
             Успешный       job failed
              deploy            │
                                 ▼
                         восстановление
                         backup-версии
```

Реализованы все основные механизмы, предусмотренные заданием:

- автоматическое развертывание на Helios;
- передача файлов через SSH и `rsync`;
- отдельный deploy SSH-ключ;
- preview-каталоги для отдельных веток;
- публикация `main` в основной каталог;
- проверка HTTP-кода `200`;
- проверка контрольной строки в HTML;
- сохранение предыдущей версии;
- ручной откат к предыдущей версии;
- обработка ситуации с обрывом передачи;
- сравнение Helios с GitHub Pages.

Таким образом, простой процесс публикации:

```text
build → upload
```

был дополнен проверкой результата:

```text
build → deploy → verify
```

а за счет резервного копирования предусмотрена возможность восстановления предыдущего состояния сайта после неудачного развертывания.
